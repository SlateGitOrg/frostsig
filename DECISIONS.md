# Design decisions

Key design decisions in frostsig, each with the reasoning and what it would cost
if it turned out wrong.

## Protocol and cryptography

- implement exactly two ciphersuites, `FROST(Ed25519, SHA-512)` and `FROST(ristretto255, SHA-512)`. — These are the two suites in scope, and both share curve25519's scalar field, so one `curve25519_dalek::Scalar` type serves both and the `Ciphersuite` trait only abstracts the group element, its encoding and `H2`. — Adding Ed448, P-256 or secp256k1 means making the scalar type an associated type, which touches every module's signatures.
- require `2 <= min_signers <= max_signers`, even though RFC 9591 permits `MIN_PARTICIPANTS = 1`. — In a 1-of-n "threshold" every share equals the group secret, which is almost always a configuration mistake. — Someone who wants 1-of-n has to use plain Ed25519, which is the right tool for that anyway.
- participant counts and the identifiers produced by key generation are `u16` (at most 65,535 participants). The decoder accepts any non-zero canonical scalar identifier. — This keeps counts in the wire format to two bytes and removes overflow edge cases. The RFC bound (less than the group order) is far beyond any practical group. — Groups above 65,535 members would need a format version bump.
- Ed25519 `DeserializeElement` also rejects non-canonical encodings by decompressing, recompressing and comparing the bytes. — RFC 8032 section 5.1.3 rejects `y >= p` and the `x = 0, sign = 1` encoding, and curve25519-dalek's `decompress` accepts both. The unit tests include these cases. — Costs one extra point compression per decode, about 1 µs.
- this crate's own `verify` uses the cofactored equation `[8][z]B = [8]R + [8][c]PK` that RFC 9591 section 6.1 requires. The CLI, simulator and tests also cross-check every Ed25519 signature with `ed25519-dalek`'s `verify_strict`. — FROST never outputs torsion components, so honest signatures pass both checks, and agreement with an independent verifier is the real interoperability claim. — If a deployment uses a cofactorless verifier and an adversary can inject torsion into R, the two verifiers could disagree. Unit test `cofactored_check_tolerates_torsion_in_r` documents this case.
- the DKG is Pedersen's DKG with Feldman VSS and Schnorr proofs of knowledge, i.e. the KeyGen of the FROST paper (Komlo & Goldberg, 2020). The proof challenge is `HDKG(id || C_i0 || R_i)` with `HDKG = H(contextString || "dkg" || m) mod L`. — RFC 9591 does not specify a DKG. This construction is the one the FROST security proof assumes, and the hash layout follows the Zcash Foundation `frost` crates. — No cross-implementation DKG test vectors exist, so interoperability of the DKG messages with other libraries is untested. The signing protocol is the interoperable part.
- binding factors, the group commitment and the challenge are computed once per session (`SigningSession`), and the group commitment uses a variable-time multi-scalar multiplication. — All of those inputs are public. Verifying all `t` shares then costs O(t) point operations instead of the O(t²) that per-share `verify_signature_share` gives, and section 4.5 of the RFC itself suggests multi-exponentiation. Secret-dependent operations, such as `base_mul` of nonces and shares, stay on dalek's constant-time paths. — If a future change routes a secret through the vartime path, timing could leak it. Code review has to watch this.
- `aggregate` verifies the final signature and checks individual shares only when that verification fails (the RFC's SHOULD and MAY). `ShareVerification::Always` is available as an option. — In the honest case this is cheaper: the benchmark table shows always-verify costing 2 to 6 times as much, growing with t. Either way cheaters are identified. — Under `OnFailure` an attacker who makes signing fail costs the coordinator one extra pass. Fine for a demo.
- `SigningNonces` is neither `Clone` nor `Copy`, `sign` takes it by value, and its scalars are zeroized on drop. — This turns the RFC's "MUST NOT use the nonce more than once" into a compile-time property instead of a runtime check. — Callers who need to persist nonces across a process restart cannot do so. That is deliberate.
- participants check that the commitment the coordinator lists for them equals the one they issued (`Error::IncorrectCommitment`). — This is the input validation that section 5.2 asks of signers. It stops a coordinator from substituting commitments. — None.

## Wire format and storage

- use a small custom binary codec (`"FS" | version | suite | tag | body`) instead of serde or postcard formats from other libraries. — It is strict and easy to audit: canonical scalars and elements, bounded lengths, no trailing bytes, and identifier lists that must be strictly ascending. A property test checks that decoding never panics. — The format does not interoperate with other FROST implementations' serialized packages, though the RFC-defined values inside are byte-identical.
- identifier-keyed lists must be strictly ascending on the wire. — The mutation property test found that an unsorted list decoded successfully (`BTreeMap` re-sorted it) but no longer round-tripped, so one value had two encodings. Requiring ascending order makes every encoding canonical. — None.
- `keygen` writes key packages as plaintext hex inside JSON, with mode 0600 on Unix and a `note` field stating that the file holds a secret. — The tool is educational, and encrypting the files at rest would need a KDF and passphrase UX that are out of scope. — Anyone who can read those files gets the shares. `docs/THREAT_MODEL.md` and the README say so.

## Simulation

- participants run on OS threads that communicate only through `std::sync::mpsc` channels carrying encoded bytes. The sender is stamped by the sending `Endpoint`, not taken from the message. — This models the authenticated (not confidential) channels that FROST assumes for identifiable abort, while still forcing a full encode, decode and validate cycle at every hop. — Real networks add reordering, loss and partial delivery. Timeouts cover loss. Reordering within one sender cannot happen here.
- DKG broadcast is modelled as n-1 point-to-point sends with no echo broadcast. — This keeps the simulator simple, and it makes the equivocation fault meaningful. Equivocation is detected afterwards: the coordinator compares every participant's group view and reports `Inconsistent`, but it cannot attribute blame. — A deployment needs a real reliable broadcast, such as echo broadcast, to identify the equivocator. This is listed under Limitations.
- the coordinator excludes culprits, retries a session up to 3 times, and tops the signer set back up with the lowest-numbered participants that are not excluded. Participants that stay silent, refuse, or send malformed bytes are also blamed. — RFC 9591 leaves the response to misbehaviour to the application (section 5.4) and suggests removing misbehaving participants from future runs. — Blaming silent participants can wrongly exclude a node that was merely slow. The timeout is configurable.
- a `--seed` derives per-role ChaCha20 RNGs through SHA-512 with domain separation by role and index. Without a seed every RNG comes from OS entropy. — The demo and the tests can then be byte-for-byte reproducible. — A seeded run is deterministic and so not secret. The CLI help says "demo only".
- CLI logging defaults to the `error` level, and `RUST_LOG=info` or `RUST_LOG=debug` shows protocol traces. — Without this, warnings from worker threads interleave with the report on the terminal in nondeterministic order. — None.

## Tooling

- dependencies are pinned with `=` (curve25519-dalek 4.1.3, ed25519-dalek 2.1.1, thiserror 1.0.69, and so on) on edition 2021. — Builds are reproducible, and these releases are widely deployed. — Security fixes must be pulled in by hand.
- the README benchmark table comes from a built-in median-of-N harness (`frostsig bench`, `make bench-table`), alongside Criterion benches (`make bench`). — One command regenerates the exact table, so the published numbers are reproducible. Criterion stays available for proper statistics. — The medians are noisier than Criterion estimates, and the measurement machine was shared with other builds. The README discloses this.
- coverage is measured with `cargo llvm-cov --all-targets` over the library and the binary, with an 80% line threshold. — The CLI and the simulator are real code paths, and the integration tests run the binary. — Some error paths, such as thread panics and channel disconnects, cannot be reached without fault injection in std itself.
- the RFC vectors are committed as a 60-line excerpt, regenerated by `scripts/extract-vectors.sh` against a SHA-256-pinned copy of the RFC text, and checked in CI. — The tests stay offline while provenance stays verifiable. — None.
